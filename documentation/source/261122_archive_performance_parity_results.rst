외부 도구 대비 압축·ISO·파일 전송 성능 결과
=======================================================

2026-11-22. 파일 관리 작업의 기준은 설치된 Total Commander이며, 전문 도구 7z.exe·oscdimg·robocopy 기준도 함께 유지한다. 종단 생성 시간은 작업 준비 시작부터 스케줄러의 최종 파일 공개 및 완료까지다. UI 대화상자와 수동 선택 시간은 제외했다. 표에는 경과 시간 중앙값(ms)을 기록했다. 전체 경로의 외부 도구 동등 성능 목표는 미달이다. 원격 ISO와 NAS 출력에서 개선 폭이 컸다. RDP 입력 ISO는 판독기만 변경한 전체 검증 A/B에서 18.44초에서 0.69초로 줄었다. NAS 출력 ZIP은 로컬 임시 생성으로 307 ms에서 70 ms로 줄었다. 로컬 7z·ZIP 기본 검증과 원격 → 로컬 소형 파일 전송에는 격차가 남는다. 로컬 → RDP의 새 폴더(23파일)는 진행 중 파일명 공개를 허용한 본체 직접 복사로 HC가 TC와 robocopy보다 60회 모두 빨랐다. 반대 방향은 중복 원본 조회를 줄이고 새 로컬 폴더에 한해 원본 읽기를 미리 준비했다. 최종 보완본 30회의 같은 완료 조건에서 HC 1,681.9 ms, TC 2,058.8 ms, robocopy /MT:8 952.5 ms였다. 30회 모두 robocopy, HC, TC 순으로 끝났다.

압축·해제·ISO·복사·이동·삭제별 원인과 수정은 `경로별 원인과 수정 내역`_ 에, 검증 수준을 맞춘 전문 도구 비교는 `기본 전체 검증의 외부 도구 대비 판정`_ 에 있다. 반복 횟수와 합격 판정 기준은 `재현 및 남은 인수 조건`_ 에 정리했다.

최종 RDP 표본은 `반복별 원시 CSV <261122_rdp_tree_publication_samples.csv>`_ 에 보존했다. 이 파일은 이전 실험·부분 회차를 포함해 1,002행이다. 최종 전후 30쌍은 60행이고, 세 도구 외부 관측은 90행이다. 기록한 원격 측정 루트 615개를 실제 D와 대조해 남은 폴더 0개를 확인했다. 원시 CSV와 설치 해시를 다시 확인한 뒤 이 작업이 소유한 로컬 측정 디렉터리의 임시 파일 2,282개(16,386,929바이트)를 정리했다. 보고서·원시 데이터·복구용 설치 백업을 보존했다.

최종 보완본을 ``D:/Utils/HyperCommander`` 에 설치했다. Release 및 설치 실행 파일의 SHA-256은 ``13B7AA1B22F6EA31B1E1540D24ADB50D0FFE2BB905554FDE694E2F44D34A9188`` 이며, 제품 PE 서명 76개와 인벤토리 해시 366개를 확인했다. 덮어쓰기 백업은 ``_build/install/bd96a9aa411d422cba563ddbb7a64697`` 에 보존했다. 같은 작업 트리의 기존 변경도 이 설치에 포함됐다.

신규 RDP 폴더의 본체 직접 복사
-----------------------------------------------------------------------

로컬 NTFS·ReFS에서 RDP로 **새 일반 폴더를 복사**할 때 본체의 폴더 전송 엔진이 최대 8개 작업자로 Windows ``CopyFile2`` 를 호출한다. RDP 목적지에는 작성 중인 파일명이 보일 수 있다. 사용자가 이 동작을 승인했다. 작업을 취소하면 쓰고 있던 파일은 제거하고 이미 끝난 파일은 남긴다. 제품의 복사 명령과 같은 작업 큐에서 검증했다.

직전에는 96,486바이트를 전송하는 데 약 5초가 걸렸다. 임시 이름의 파일마다 조상 폴더를 다시 열고, 원격에서 최종 이름으로 변경하고 다시 검증해야 했다. 새 폴더 엔진은 소스와 목적지의 조상 폴더를 고정한 뒤, 열린 부모 핸들을 기준으로 새 디렉터리를 단 한 번 생성한다. 생산한 파일은 새 이름으로 직접 복사한다. 원본 파일은 복사 호출 동안 쓰기·교체를 막고, 로컬 열거 때의 파일 ID·크기·시각·속성을 다시 대조한다. 늦게 생긴 같은 이름을 덮어쓰지 않는다.

호스트 재부팅 전 설치와 검증 범위, 미완료 회차 및 재개 절차는 `재부팅 체크포인트 <261122_file_io_reboot_checkpoint.rst>`_ 에 저장했다.

**제품 전후 비교.** 목적지에 외부 관측기를 붙이지 않고, 상세 계측을 끈 두 실행 파일을 실제 D 드라이브에서 순서를 바꿔 8쌍 비교했다. 스케줄러 완료 중앙값은 **4,628.6 → 981.3 ms (78.8% 단축)** 였다. 8쌍 모두 빨라졌다. 이전 범위는 4,396.6–4,718.0 ms, 개선 후 범위는 791.5–1,290.3 ms였다. 빌드가 동시에 실행된 표본은 없었다. 두 빌드 모두 모든 파일의 전체 내용이 일치했다. 별도 상세 계측에서 조상 경로를 여는 함수 호출은 28회에서 2회로 줄었다. 이전에는 파일별 확정이 23회였고 새 경로에서는 직접 복사가 23회였다. 디렉터리 5개를 각각 열어 처리했으며, 이 함수 호출 횟수를 네트워크 패킷 수로 환산하지 않았다.

**Total Commander 및 robocopy 비교.** 설치된 32비트 Total Commander 11.58, Windows robocopy /MT:8, HC를 실행했다. 6가지 도구 순서를 5번씩 사용했다. 매번 비어 있는 전용 경로에서 시작해 같은 이름·크기의 23파일이 모두 존재하고 각각을 기존 쓰기 핸들과 공유하지 않는 읽기 모드로 열 수 있을 때까지 같은 관측기로 측정했다. 쓰는 중에도 최종 이름과 크기가 나타날 수 있어 이름·크기만으로 타이머를 멈추지 않았다. 마지막 관측이 끝나야 전체 내용 해시와 폴더 구조 검사를 시작한다. 이 절의 진단 실행을 제외한 비교에서는 상세 계측을 껐다.

**적용 조건과 검토 반영**

* 기존 폴더 병합, 단일 파일, 이동, 원격 원본, 일반 SMB 목적지, 필터·속도 제한·SHA 검증·ACL·대체 스트림·복구 기록·강제 플러시에는 기존 경로를 사용한다. 일반 파일의 보관 속성만 있는 경우 직접 복사하고 다른 속성의 파일은 같은 작업 안에서 기존 경로가 처리한다. 실제 RDP에서 숨김 속성만 있는 원본에 ``CopyFile2`` 가 보관 속성을 추가한 것을 확인해 이 분기를 넣었다. 작업 트리 네 소스 디렉터리의 추적 C/C++ 파일 1,189개는 모두 보관 속성만 있었다. 사용자 데이터에서의 적용 비율은 파일 속성에 따라 달라진다.
* 목적지를 변경하기 전에, 직접 부모를 읽기 공유로 고정한 상태에서 삭제·자식 추가 권한으로 다시 여는 두 시도가 공유 위반으로 거절되는지 확인한다. 공유 모드가 확인되지 않으면 기존 경로로 돌아간다. DEVTESTER-SVR의 D 루트에서도 두 요청 모두 Windows 오류 32였다. 이름이 이미 생겼거나 권한이 부족한 항목은 기존 충돌·권한 처리로 전달한다.
* Claude 재검토에서 UI 기본 권한 상승 설정 때문에 일반 F5 복사가 직접 경로에 들어가지 못하는 조건을 발견해 제거했다. 권한 지원을 켠 요청으로 제품 큐를 실행해 일반 파일의 직접 처리, 숨김·읽기 전용 파일의 원래 속성과 지정된 수정 시각, 기존 폴더 병합의 직접 처리 제외를 검사했다. 실제 RDP에서 32 MiB 파일명이 보인 직후 취소해 미완성 파일이 사라지고 직전에 끝난 파일의 바이트는 남는 것도 확인했다. 열린 새 폴더에 다른 작업이 같은 이름을 먼저 생성한 시험에서는 해당 항목을 충돌 처리로 넘기고, 경쟁 파일과 이미 완료된 파일의 바이트를 모두 보존했다. 강제 플러시 요청은 폴더 생성 전에 직접 경로에서 제외됐다. 실제 RDP의 전송 시험은 초기화·종료 포함 5건, 쓰기·복구 시험은 3건 통과했다. 지정 VM에서는 전송 11건과 쓰기 26건이 통과했다. VM에서 건너뛴 RDP 전용 전송 시험 3개는 호스트의 실제 RDP 세션에서 실행했다.

RDP 원본에서 로컬로 복사할 때의 중복 조회
-----------------------------------------------------------------------

같은 23파일을 반대 방향으로 복사한 본체의 상세 계측에서 전체 작업은 2,271.2 ms였다. 원본 열기 23회의 작업자 누계는 2,299.5 ms, Stat 51회는 1,442.4 ms, 실제 파일 읽기 23회는 239.4 ms였다. 목적지 파일 확정 23회는 10.3 ms였다. 작업자 시간이 겹치므로 각 누계의 합은 전체 경과 시간과 다르다.

RDP는 SMB 공급자를 통해 접근한다. 일반 복사를 준비할 때 이 공급자는 폴더를 열거하며 각 자식의 핸들에서 이미 생성 시각·수정 시각·크기·속성을 읽었다. 작업 계획기는 그 사실을 알 수 없어 4개 하위 폴더와 23개 파일을 다시 조회했다. 변경한 본체는 RDP 디렉터리의 모든 자식 조회가 성공한 열거 페이지에 정보를 남긴다. 복사 작업은 이 페이지에서 얻은 리비전을 재사용한다. 선택한 루트, 열린 원본 핸들, 읽기 완료 후의 변경 검사를 유지한다. 일반 SMB, 셸 목록, 삭제·이동 작업은 기존 동작을 따른다.

실제 DEVTESTER-SVR D에서 상세 계측을 다시 실행해 Stat 호출이 **51 → 24회**로 줄어든 것을 확인했다. 23개 데이터 핸들 열기와 23회 본문 읽기는 유지됐다. 새 계측에서 Stat 작업자 누계는 927.0 ms, 원본 열기는 1,905.3 ms, 본문 읽기는 155.1 ms였다. 예전 상세 계측은 재부팅 전 빌드 프로세스가 동작할 때 수집했다. 종단 개선율은 아래와 같이 재부팅 후에 순서를 바꾼 비교로 계산했다.

외부 관측기 없이 전후 실행 파일을 교대시킨 8쌍에서 스케줄러 완료 중앙값은 **2,335.9 → 1,726.2 ms (26.1% 단축)** 였다. 개선 후 범위는 1,613.4~1,816.2 ms였고 8쌍 모두 빨라졌다. 전체 출력 내용·폴더 구성 검사를 통과했으며, 이 전후 비교 시 빌드 프로세스는 검출되지 않았다. 같은 코퍼스에서 robocopy 프로세스 종료 시간은 4회 중앙값 963.9 ms였다.

같은 완료 관측기로 재부팅 후 세 도구를 순서를 바꿔 6회 측정했다. 로컬 출력에서 23개 파일의 이름·크기와 쓰기 핸들 닫힘을 확인한 중앙값은 **HC 1,692.4 ms, TC 2,030.9 ms, robocopy 896.8 ms**였다. HC가 TC보다 6회 모두 빨랐고 robocopy가 HC보다 6회 모두 빨랐다. 짝별 HC/TC 비율의 중앙값은 0.826, HC/robocopy는 1.822였다. robocopy가 비교한 원본 메타데이터의 호출 횟수는 측정하지 않았다. 원시 표본에서 ``rdp_source_copy`` 는 외부 관측기 없는 전후·robocopy 실험이고, ``rdp_source_matched`` 는 같은 완료 관측기를 붙인 세 도구 비교다.

작업자 수의 영향을 확인하려고 같은 RDP 입력을 실행 순서를 바꿔 방식마다 5회씩 복사했다. 스케줄러 또는 프로세스 종료 중앙값은 HC 단일 작업자 2,571.3 ms, HC 자동(선호 작업자 8) 1,722.2 ms, robocopy 기본 1,772.5 ms, robocopy /MT:8 950.8 ms, Win32 재귀 복사 1,504.7 ms였다. HC의 자동 병렬 처리와 robocopy의 /MT:8 모두 효과가 있었으며, 작업자 수를 8로 맞춰도 격차가 남았다. 모든 출력의 내용을 검증했다. 이 25건은 Release 빌드 중의 보조 실험이며 원시 행은 ``rdp_source_workers`` 다.

빈 Claude 세션에서 선택 루트·재시도·이동·오류·캐시 페이지 경로를 검토했다. 실제 RDP 시험에서 일반 목록은 검증 표식을 발행하지 않았고, 검증한 목록 이후 파일을 늘리자 고정 읽기 핸들에서 리비전 불일치를 검출했다. 별도 취소 시험은 첫 실행에서 이름이 보인 뒤에도 파일이 남아 실패했다. 그 시점에 복사가 끝났는지 알 수 없어 시험을 보완했다. 이제 작업자가 진행 콜백 안에서 목적지 쓰기 핸들과 충돌하는 읽기 열기를 확인하고 일시정지한다. 취소 후 목적지를 새 핸들로 열어 파일 없음 오류를 확인하고, 직전에 완료한 파일의 내용도 검사한다. 보완 후 실제 RDP 전송 시험 6건과 쓰기·복구 시험 3건이 통과했다(초기화·종료 포함). 취소 단독 재실행 4회도 통과했다. 지정 VM에서는 전송 11건과 쓰기 26건이 통과했으며, RDP 전용 전송 시험 4건은 호스트에서 실행했다.

메타데이터 읽기 두 번을 한 번으로 줄이는 후보도 같은 권한으로 열어 시험했다. 로컬 NTFS에서는 ``FileNetworkOpenInformation`` 한 번으로 두 조회와 같은 값을 얻었다. 실제 RDP의 같은 호출은 첫 파일에서 ``0xC000000D`` 를 반환해 이 방식을 채택하지 않았다. 남은 비용 중 고정 읽기 핸들 열기와 확인에 작업자 누계 1.91초가 걸렸다. 병렬 작업자 누계이므로 1.91초를 그대로 종단 절감 가능 시간으로 잡을 수 없다.

후속 후보인 **원본 읽기 핸들 재사용**도 독립 실행기로 확인했다. 23파일에 최대 8개 작업자를 사용했다. 두 방식 모두 원본의 크기·시각·속성을 확인하고 로컬 임시 파일에 쓴 뒤 원본의 최종 경로를 다시 검증하고 파일별로 공개한다. 원본 핸들을 닫았다가 다시 열어 검증하는 방식은 1,873.4 ms, 같은 핸들을 읽기까지 유지하는 방식은 1,424.0 ms였다(6쌍 중앙값, 24.0% 단축). 6쌍 모두 빨랐고 출력 전체 SHA-256이 일치했다. 이 실험은 Release 빌드 중 수행했으며 작업 큐·충돌 질문·취소·재시도 비용을 포함하지 않는다. 제품의 1,692.4 ms에서 이 절감액을 빼서 예상 성능을 계산할 수 없다. 원시 행은 ``rdp_source_pin_prototype`` 이다.

별도 진단에서 원본 열거 후 같은 핸들 속성 조회를 폴더마다 1개 또는 최대 8개씩 실행했다. 순서를 바꾼 8쌍의 중앙값은 760.5 ms와 571.4 ms였다. 양쪽 모두 파일 23개의 속성·크기·시각이 일치했다. 이는 원본 열거와 속성 조회만을 잰 값이다. 이 진단의 병렬화는 제품 변경에 포함하지 않았다.

새 로컬 폴더로 복사할 때 RDP 원본 미리 열기
-----------------------------------------------------------------------

사용자가 허용한 범위에서, 이번 작업이 직접 만든 로컬 폴더로 일반 파일을 복사할 때 다음 원본을 최대 8개까지 읽기 전용으로 연다. 기존 폴더 병합과 단일 파일 복사에서는 종전 시점에 원본을 연다. 미리 열어 둔 파일은 읽기가 끝날 때까지 다른 프로그램의 쓰기·이름 변경이 제한될 수 있다. 복사 작업자는 준비된 핸들을 넘겨받고 파일을 공개하기 전에 원본의 최종 경로와 리비전을 대조한다. 열거 시점의 속성 핸들과 데이터를 읽는 핸들은 각각 연다. 제품에서 줄인 비용은 데이터 핸들이 준비될 때까지 기다리는 시간이다.

검토 전 빌드에서 미리 열기만 추가한 짝지은 8회가 전부 빨랐다. 중앙값은 **95.6 ms(5.6%)** 줄었다. 외부 도구와 순서를 바꿔 비교한 6회에서는 HC가 TC보다 매번 빨랐고, robocopy가 HC보다 매번 빨랐다. 같은 관측기의 중앙값 기준으로 HC는 robocopy의 1.87배 시간이 걸렸다. 전후 비교 시작 시 MSBuild 프로세스 3개가 감지됐다. 전체 내용은 각 회차에서 대조했다. 6회는 방향을 확인하는 표본이며, 정식 인수의 반복 횟수는 30회다.

상세 계측 1회에서 원본 열기 23회, 실제 읽기 23회, Stat 24회를 기록했다. 독립 실행기의 핸들 재사용 24.0%와 제품의 대기 중첩 5.6%는 서로 다른 변경이다. 제품은 원본의 각 하위 항목을 열어 속성을 얻고 읽은 뒤 최종 경로도 다시 점검한다. 외부 도구의 내부 호출을 추정해 잔여 시간 전체를 이 두 단계에 배분할 수 없다. 원시 표본은 ``rdp_source_read_ahead`` 와 ``rdp_read_ahead_matched`` 에 있다.

실제 D에서 12개 파일로 쓰기 개방을 시도해 동시 잠금 최대 8개를 확인했다. 새 목적지에서는 12개 모두 준비된 핸들로 읽었고, 기존 폴더에 합칠 때는 미리 열기 0건이었다. 같은 이름을 복사 도중 만들어 충돌 질문이 표시될 때 잠금이 0개임을 검사했고 경쟁 파일의 내용을 보존했다. 8번째 원본을 연 시점에 취소한 뒤 잠금과 미완성 임시 파일이 남지 않았음을 확인했다. 실제 RDP 전송 시험 7건·쓰기 및 복구 3건이 통과했다. 지정 VM에서는 전송 11건·쓰기 26건이 통과했다. VM의 리디렉션 경로 전용 시험 5건은 호스트의 실제 RDP에서 실행했다. 각 실행 건수에는 초기화와 종료가 포함된다.

**독립 검토와 회귀 수정.** 새 Claude 세션에서 소스 리비전·충돌·취소 경계를 검토한 결과, 16 MiB 초과 파일을 직렬로 복사하는 동안 뒤의 작은 파일을 오래 잠글 수 있다는 지적이 나왔다. 최종 구현은 직렬 파일 앞에서 미리 열기를 멈춘다. 커밋 단계에서는 새 핸들을 요청하지 않으며, 미리 열기에 실패한 사이 취소·기한 초과가 발생하면 해당 오류를 우선 반환한다. 일시정지 신호로 미사용 핸들을 닫고, 재개 후에는 새 신호를 사용한다. 두 원본이 같은 목적지 폴더 이름으로 합쳐질 때 각 원본의 선택 루트를 구별해 실제로 폴더를 생성한 쪽에만 미리 열기를 허용한다.

검토 후 실제 RDP에서 8번째 핸들을 여는 중에 일시정지하고 작은 원본의 쓰기 잠금이 0인 것을 검사했다. 재개 후 전 파일 내용이 일치했다. 16 MiB + 1바이트인 파일을 여는 도중 그 뒤에 있는 작은 원본의 잠금은 0이었다. 미리 열기 실패를 한 번 주입했을 때 일반 열기 한 번으로 완주했다. 같은 이름의 두 원본 폴더를 한 작업으로 복사했을 때 미리 열기 1건·일반 열기 1건이었고 두 파일 내용이 보존됐다. 지정 VM에서 작업 스케줄러 50건, 전송 11건, 쓰기 26건을 통과했다.

**검토 반영 전후 30쌍.** 상세 계측과 외부 관측기를 끄고, 중복 Stat만 줄인 직전 HC와 새 폴더 미리 열기를 포함한 최종 HC를 교대로 실행했다. 스케줄러 완료 중앙값은 **1,747.6 → 1,651.1 ms**였다. 96.5 ms(5.5%) 단축됐고 30쌍 중 24쌍에서 빨랐다. 짝별 시간비는 중앙값 0.951, 20번째 값 0.963, p95 1.044였다. 1~8회에는 빌드 도구 프로세스가 감지됐다. 감지 개수 0인 9~30회만 계산하면 1,754.6 → 1,638.9 ms, 18/22쌍에서 개선됐다. 모든 회차에서 23개 파일의 바이트와 폴더 구성을 검증했다. 최종 상세 계측에서도 원본 열기 23회·본문 읽기 23회·Stat 24회였다. 원시 행은 ``rdp_read_ahead_final_ab`` 이다.

**최종 설치 후 30회.** 세 도구의 가능한 6가지 실행 순서를 다섯 번씩 바꿨다. 23개 일반 파일·96,486바이트의 출력에서 이름·크기·쓰기 핸들 닫힘을 같은 관측기로 확인했다. 중앙값은 **HC 1,681.9 ms, Total Commander 2,058.8 ms, robocopy /MT:8 952.5 ms**였다. HC는 TC보다 30/30회 빨랐고 robocopy보다 30/30회 느렸다. 짝별 시간비 HC/TC는 중앙값 0.808, 20번째 값 0.830, p95 0.893이었다. HC/robocopy는 각각 1.790, 1.829, 2.093이었다. 데이터는 ``rdp_read_ahead_final_matched`` 에 있다. HC는 제품 작업 큐에서 실행했으며 패널 조작 및 화면 갱신 시간은 포함하지 않는다.

18회차 첫 시도에서 HC가 복사와 전체 내용 검증을 마쳤지만 외부 관측기가 목적지 경로를 알려주는 로컬 파일을 읽을 때 Windows 공유 위반이 발생했다. 어느 프로세스가 파일을 점유했는지는 확인하지 못했다. HC 스케줄러 시간 1,524.7 ms, robocopy의 내부 시간·외부 관측, TC의 외부 관측을 별도 계열 ``rdp_read_ahead_incomplete_observer`` 에 보존했다. 관측기의 일시적 공유 위반 재시도를 추가하고 세 도구를 모두 재실행했다. 위 30회는 세 결과가 모두 있는 회차만 포함한다.

직전 단계 · 파일별 공개와 비공개 폴더 실험
-----------------------------------------------------------------------

여기부터는 각 변경 시점의 빌드와 기준선이다. 새 RDP 폴더의 최종 제품 수치는 첫 절을 사용한다.

로컬 NTFS에서 실제 리디렉션 드라이브 `D on DEVTESTER-SVR`로 23개 파일과 하위 폴더 4개, 총 96,486바이트를 복사했다. HC는 본체의 파일 작업 큐를 사용한다. 이 경로에는 플러그인 호스트나 7z 코덱이 개입하지 않는다. 8회씩 순서를 바꾼 비교에서 각 도구는 매번 새 목적지를 사용했다.

**원인과 반영 내용.** 파일 내용을 모두 합쳐도 95 KiB 미만이지만, HC는 파일마다 조상 폴더를 열어 재분석 지점인지 검사하고 비공개 임시 파일을 최종 이름으로 공개한다. 이후 쓰기 핸들을 닫고 새 이름을 열어 파일 종류·크기·수정 시각을 확인한다. 변경 전에는 이 확인 뒤에 조상 핸들을 닫았다. 이제 신규 RDP 파일에 한해 최종 이름을 연 뒤 **최종 핸들 확인과 조상 핸들 해제를 병행**한다. 그 파일만 소유하는 조상 핸들이 네 개 이상인 경우에 적용하며 모두 끝나면 완료를 알린다. 속성이나 요청 시각을 보정해야 하면 같은 최종 핸들을 유지한다. 기존 파일 교체, 복구 기록, 공개 핸들 보유 및 강제 플러시에는 적용하지 않는다.

**제품에 적용하지 않은 후보와 그 이유**

* 폴더 전체를 같은 부모의 임시 이름에 만든 뒤 한 번에 공개한 실험은 성공한 5회의 중앙값이 1,664.9 ms였다. 나머지 1회는 최종 폴더 이름 변경에서 Windows 오류 5로 실패했다. 중간에 한 파일까지 완료하고 취소하면 최종 위치에 남은 파일이 0개였다. 기존 HC는 완료 파일을 남긴다. 도중 다른 작업이 만든 목적지와 그 내용은 덮어쓰지 않았다. 이 방식은 빠르더라도 현재 복사의 결과 계약을 충족하지 못한다. 임시 폴더를 한 겹 더 둔 초기 후보도 6회 중 1회 공개에 실패했다.
* 마지막 쓰기 핸들을 열어 둔 채 새 이름을 확인한 후보는 2쌍 중앙값 5,218.8 → 4,461.9 ms였다. 최종 쓰기 핸들이 닫힐 때까지 수정 시각이 확정되지 않을 수 있다는 Claude 검토를 반영해 폐기했다. 쓰기 핸들을 닫은 뒤 본문 읽기 권한으로 다시 여는 후보는 6쌍에서 5,226.2 → 5,254.0 ms였다.
* 새 파일에 대해 쓰기 핸들을 닫은 뒤 속성 읽기·쓰기와 삭제 권한만 요청하고 최종 핸들과 조상을 함께 닫은 중간 후보는 8쌍에서 5,082.7 → 4,914.8 ms였다. 같은 시점 TC 기존 관측법 3회 중앙값은 4,899.2 ms, robocopy /MT:8은 1,545.3 ms였다. 서로 완료 검출 방법이 다른 이 수치로 TC 동등 판정을 내리지 않았다.
* 조상 폴더 핸들을 파일 사이에 공유하는 별도 시험에서는 실제 RDP에서 목록 읽기 권한과 읽기 공유만 허용한 핸들이 조상 교체와 정상적인 자식 이름 변경을 모두 막았다(Windows 오류 32). 이 핸들을 다음 파일까지 유지하는 방안은 적용하지 않았다.

* 같은 최종 핸들 권한으로 크기와 기본 속성을 한 번에 조회하는 방식도 시험했다. ``FileAllInformation``과 기존 두 조회가 반환한 크기·속성·생성·접근·수정 시각은 32쌍 모두 같았다. 조회만의 중앙값은 9.31 → 8.68 ms였다. 23파일의 종단 격차를 설명하기에는 작고 제품 복사의 전후 차이를 입증하지 않아 이 후보를 기본값에 넣지 않았다. `Microsoft 파일 정보 조회 명세 <https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntqueryinformationfile>`_

**파일별 직접 복사 실험.** 본체에서 사용할 수 있는 Windows ``CopyFile2`` 를 8개 작업자로 호출하는 독립 실행기를 만들었다. 새 목적지의 조상·하위 폴더를 한 번씩 열어 일반 디렉터리인지 확인하고 복사가 끝날 때까지 핸들을 유지했다. 덮어쓰기 금지와 대체 데이터 스트림 생략을 지정했다. 다섯 번 모두 23파일의 이름·길이·SHA-256·속성·수정 시각과 폴더 구성이 일치했다. 중앙값 **916.0 ms** 였다. 여기에는 소스 열거, 폴더 생성·확인, 파일 복사와 핸들 해제가 포함된다. 제품 큐·충돌 대화·재시도·완료 통지는 포함하지 않는다. 재현기는 ``tools/Measure-RdpPinnedCopy.ps1`` 이다.

16 MiB 복사 중 진행 콜백에서 목적지 파일명이 이미 보이는 시점에 취소했다. API가 작업 중단을 반환하고 미완성 파일을 제거했으며 직전에 완료한 파일은 남았다. 별도 목적지 충돌 시험에서는 기존 파일 바이트가 유지됐다. 제품의 준비 파일은 성공적으로 확정할 때 최종 이름이 나타난다. 독립 실행기 측정은 제품 성능 집계에서 분리했다. 이후 사용자가 진행 중 이름 공개를 승인해, 제품에 통합한 경로는 이 보고서 첫 절에서 따로 측정했다. 새 폴더라는 조건만으로는 중간 공개 여부까지 같아지지 않는다.

**측정 방법.** 변경 전후 제품 속도는 목적지 외부 관측기 없이 같은 상세 계측에서 비교한다. TC와 HC의 가시 시점 비교에서는 명령 발행 또는 HC 원본 Resolve 진입 직전의 시스템 성능 카운터를 시작점으로 삼는다. 두 도구에 같은 관측기를 연결해 기대한 모든 파일명과 길이가 열거된 시각을 잰다. 관측이 끝난 후 전체 파일 SHA-256과 폴더 구성을 검사한다. 제품 전후 원인 분석에서는 상세 계측을 켰고 TC와의 최종 비교에서는 제품 기본 상태처럼 상세 계측을 껐다. HC의 스케줄러 완료도 별도로 기록한다. TC 내부 스케줄러의 종료 시각, 화면 갱신 시각, 디스크 강제 플러시까지의 시간은 이 비교로 알 수 없다. 첫 관측 실험에서는 HC의 해시 검사가 관측기의 마지막 디렉터리 열거와 겹칠 수 있어 판정에서 제외했다. 최종 하네스는 관측 종료 신호를 받은 뒤 해시 검사를 시작한다.

**재현과 원시 표본.** TC 측정기는 ``tools/Measure-TotalCommanderIo.ps1 -Operation copy -CopyTree <코퍼스> -SourceRoot <로컬> -DestinationRoot <RDP> -Repeats 1`` 로 실행한다. HC는 ``hc_file_transfer_bench_tests transfer:qt-repo`` 에 ``HC_TRANSFER_BENCH_SCALE=0.001``, ``HC_TRANSFER_BENCH_OPERATIONS=copy-cross``, ``HC_TRANSFER_BENCH_IMPLEMENTATIONS=hypercommander-auto`` 를 지정했다. 양 끝 경로는 같은 접두사의 ``ROOT`` 와 ``OTHER_ROOT`` 다. ``HC_TRANSFER_BENCH_OBSERVATION`` 에 새 로컬 표식 경로를 주면 내용으로 목적지 경로를 읽을 수 있다. 양쪽 모두 ``tools/Measure-VisibleCopyTree.ps1`` 의 ``Measure-VisibleTree`` 를 사용하고, HC 실행기는 관측 직후 표식 뒤에 ``.done`` 을 붙인 파일을 생성한다. 양쪽 복사마다 표식과 목적지를 새로 만든다.

원시 CSV에서 ``no_observer`` 는 외부 관측기 없는 제품 전후·robocopy 비교이고, ``matched_observer`` 는 보정된 양쪽 관측이다. ``HC_scheduler`` 와 ``HC_visible`` 는 같은 복사의 두 시각이다. ``last_incomplete_ms`` 는 마지막으로 파일 집합이 불완전했던 열거의 **시작** 시각이며, 완료 관측까지의 차이에 원격 열거 시간도 들어간다. ``pilot_verification_overlap``, ``build_warmup``, ``observer_with_profiling`` 은 각각 해시 검증 중첩, 빌드 중 예비 실행, 상세 계측 사용으로 최종 비교에서 제외했다. ``metadata_query`` 는 복사 대신 파일 속성만 조회한 진단이다. 비공개 폴더 공개 실패는 오류 문자열과 함께 원시 행에 남겼다. `RDP 폴더 공개 실측 CSV <261122_rdp_tree_publication_samples.csv>`_

**독립 검토.** 빈 Claude 세션에서 검토한 후 측정용 임시 폴더가 실제 목적지의 ACL을 상속하도록 위치를 바꿨다. 최종 구현의 재검토에서는 쓰기 핸들을 닫는 순서, 병렬 반복 중 핸들 참조의 수명, 속성 보정과 오류 전달 경로를 확인했다. 무효 핸들 닫기 방어를 복원했고, 새 이름의 종류·크기·시각이 예상과 다르면 기존대로 오류를 반환한다. 크기만 같은 다른 파일을 수정할 수 있어 확인 실패 후 임의로 시각을 덮어쓰지 않는다.

* **로컬 → RDP.** 기존 복사는 파일마다 비공개 임시 파일의 속성 설정·조회와 최종 이름 확정, 조상 디렉터리 핸들 해제를 순서대로 기다렸다. 개선 후에는 일반 신규 복사에서 임시 파일의 메타데이터를 파일별 작업자가 미리 준비한다. 복구·덮어쓰기·최종 핸들 보유·강제 플러시가 필요한 경우에는 기존 절차를 거친다. 실제 이름 공개는 기존 순서를 지키며, 최종 이름으로 다시 열어 종류·크기·수정 시각을 비교한다. 이후 그 파일만 소유한 조상 핸들은 동시에 닫고 모두 끝나면 완료를 알린다. 독립 실험에서 7개 핸들 닫기는 12쌍 중앙값 29.54 → 19.48 ms였다.
* **수정 시각과 종단 성능.** 조상 핸들을 동시에 닫은 초기 후보는 5,443.4 → 4,569.0 ms였으나 고정된 수정 시각을 보존하지 못해 배포 수치에서 제외했다. 최종 이름에서 시각을 보정한 후보는 5,479.0 → 5,035.4 ms였다. 실제 RDP의 별도 핸들 시험에서 기본 정보와 속성을 함께 설정하면 핸들을 닫은 뒤 요청한 시각이 남지 않았고, 시각을 별도로 설정하면 열린 핸들과 닫은 파일 양쪽에 남았다. 최종 빌드는 병렬 작업자가 비공개 파일에 시각을 명시적으로 설정하고, 공개 후 관측이 다를 때만 최종 핸들에서 보정·재확인한다. 세 단계는 각각 같은 시점의 변경 전 빌드와 교대로 측정했다.
* **채택하지 않은 후보.** 임시 파일 준비만 옮긴 실험은 5,381.9 → 5,146.7 ms였다. 최종 이름을 경로 속성만으로 확인한 별도 후보는 직전 빌드 대비 5,282.7 → 4,998.5 ms였다. 리디렉터의 캐시 값으로는 방금 공개한 객체를 확인하기 어려워 최종 빌드는 새 핸들에서 확인한다.
* **RDP → 로컬.** HC는 복사 엔진을 고르는 과정에서 스트리밍만 지원하는 RDP 원본의 속성을 재조회했다. 이제 원본 리비전이 RDP임을 나타내면 바로 스트리밍을 선택한다. 잠긴 읽기 핸들에서 원본을 확인하고, 속성·크기만 필요한 조회에서는 해당 정보만 요청한다. 변경 전후 8쌍의 중앙값이 8.7% 줄었고 TC와는 여전히 101.6 ms 차이가 난다.
* **NAS → 로컬.** 원본을 쓴 직후 HC를 실행했을 때 411.8 → 412.6 ms였고 독립 TC 프로세스를 준비한 뒤 복사하면 194.5 ms였다. 6쌍의 세부 계측에서 기본 네이티브 복사는 종단 407.1 ms 중 본문 복사가 365.7 ms였으며, 강제 스트리밍은 392.6 ms 중 본문 읽기가 360.2 ms였다. 엔진을 바꿔도 본문 비용이 남아 기본 엔진을 유지했다.
* **입력 생성 시점을 맞춘 추가 비교.** 방금 생성한 원본은 TC 패널을 준비하는 동안에도 시간이 흐른다. 양쪽 모두 원본을 닫은 뒤 최소 2.5초가 지나 복사를 시작하자 NAS 30쌍에서 HC는 194.68 ms, TC는 194.50 ms였다. 대응 비율 중앙값 0.999, 20번째 값 1.018, p95 1.125였고 16쌍에서 HC가 더 빨랐다. 중앙값 차이는 0.18 ms이며, 상한이 1을 넘고 동일 도구 반복으로 잡음 폭을 교정하지 않아 정식 합격은 보류한다. 약 2배였던 최초 격차는 같은 입력 경과 시간에서 재현되지 않았다. 제품은 입력 파일을 기다리지 않는다. 동일한 2.5초 조건의 중간 RDP 6쌍은 HC 296.1 ms, TC 210.7 ms였다. 배포본과 TC를 다시 교대한 6쌍은 HC 275.1 ms, TC 189.6 ms로 85.5 ms의 차이가 남았다. 이 최종 HC 계열은 상세 계측을 켰다. 이후 RDP 리비전에 한해 파일 ID 조회를 줄인 변경만 교대한 추가 6쌍에서는 속성 재확인이 47.0 → 39.3 ms, 전체 복사가 279.9 → 277.5 ms였다.
* **측정과 판정.** HC는 제품 파일 작업의 Resolve부터 스케줄러 완료까지 측정했다. TC는 독립 인스턴스의 복사 명령부터 출력 완료를 관측했다. 폴더와 초기 단일 파일 비교는 각 3회, 입력 경과 시간을 맞춘 최종 단일 파일 비교는 RDP 6회와 NAS 30회다. 각 도구는 전용 빈 폴더를 사용했다. 최종 폴더 복사는 파일 목록·크기 및 바이트 해시를 검사했고 단일 파일은 전체 바이트를 검증했다. HC 폴더는 세부 계측을 켰으며 여러 작업자의 누적 시간은 서로 겹친다. 최종 TC 폴더는 마지막 미완료 관측 시작부터 완료 확인까지 중앙값 778.7 ms가 걸렸다. 최종 HC는 TC의 완료 관측 중앙값보다도 126.8 ms(2.6%) 오래 걸렸다. 표본 수와 완료 관측 방식의 차이를 함께 고려해 이 행은 목표 미달로 남긴다. 최종 회차의 robocopy /MT:8 중앙값은 1,534.4 ms이며 HC가 3.25배 오래 걸렸다.
* **독립 검토에서 반영한 수정.** 충돌 응답 후 작업자가 새 이름을 결정하는 중에 조정자가 같은 문자열을 읽을 수 있었다. 조정자는 대기열 등록 시점의 목적지 키를 사용하고 해당 항목의 충돌 처리가 끝날 때까지 추가 등록을 미룬다. RDP 시험에는 실제 일반 복사의 영수증 식별자 생략, 숨김·보관 속성과 원래 수정 시각 확인을 추가했다. 그 결과 RDP가 임시 파일의 결합된 속성 변경을 수락해도 수정 시각이 마지막 쓰기 시각으로 남을 수 있음을 재현했다. 최종 이름의 핸들에서 확인된 시각과 요청이 다르면 명시적으로 시각을 적용하고 다시 읽어 검사한다.
* **남은 격차의 개선 순서.** 소형 RDP 복사에는 플러그인 호스트가 관여하지 않는다. 다음 비용은 파일마다 조상 폴더를 열고 검증하는 시간이다. 먼저 새 폴더에 충돌 없이 복사하는 경우로 한정해, 본체가 비공개 트리를 준비하고 최종 폴더를 한 번에 공개하는 방식의 왕복 수를 비교한다. 취소 시 이미 공개된 항목 처리, 대상 이름 충돌, 디렉터리 교체에 대한 기존 결과를 지킬 수 있는 조건을 확인해야 한다. 원격 단일 파일 입력에서는 원본 핸들 고정·리비전 확인과 본문 읽기를 따로 줄이고, 다음으로 로컬 ZIP 단건 해제와 NAS ISO의 본체·호스트별 구간을 비교한다.
* **회귀 검증.** iMonAGR-Win11에서 전송 11건과 쓰기 28건이 통과했다. 실제 RDP 세션에서 준비 후 취소, 읽기 전용·숨김·보관 속성, 두 가지 최종 시각 조회, 공개·복구 경로를 포함한 테스트도 통과했다. 원시 표본에는 각 경로의 반복별 소요 시간, TC 완료 관측 구간, HC 폴더의 누적 단계 시간과 동시 빌드 프로세스 수를 수록했다. `RDP·NAS 원시 표본 <261122_rdp_small_copy_samples.csv>`_

**설치.** 지정 Qt 6.12 Release 빌드를 D:/Utils/HyperCommander에 설치했다. 서명된 PE 76개와 인벤토리 해시 366개를 확인했고, 설치한 HyperCommander.exe의 SHA-256은 빌드 결과와 일치했다. 설치본에는 같은 작업 트리의 다른 변경도 포함된다. 교체한 파일의 백업은 ``_build/install/57c4a9a626db487584f3ea09c4043e67`` 에 있다. 이번 작업의 로컬·VM 임시 실행환경을 정리했고, RDP와 NAS에서 작업용 폴더가 남지 않았음을 확인했다. 반복별 표본 260행은 CSV로 보존했다.

실제 파일 작업에서 다시 측정한 RDP ZIP 해제
-----------------------------------------------------------------------

**판정은 보류한다.** 로컬 ZIP을 DEVTESTER-SVR의 D로 해제한 30쌍에서 HC의 중앙값은 428.5 ms였고 TC의 완료 관측 중앙값은 522.1 ms였다. HC가 TC의 관측값 이하인 쌍은 28개였다. 쌍별 HC/TC 중앙값은 0.841, 20번째 순서통계량은 0.878이다. TC에서 직전 미완료 폴링 시작과 완료 확인 사이의 간격은 중앙값 180.8 ms였다. HC가 직전 미완료 폴링 시작 시각보다도 빨랐던 쌍은 1개다. 두 프로그램의 완료 감지 방식 차이가 중앙값 간격보다 크므로 이 행을 정식 동등 성능 달성으로 집계하지 않았다.

RDP는 파일을 최종 이름으로 옮긴 뒤 기존 핸들로 한 속성 작업이 이전 이름을 참조할 수 있어 최종 이름을 다시 열어 확인한다. 이때 크기·시각·속성만 조회하고, 재조회가 지원되지 않으면 기존 조회로 대체했다. 최종 핸들에서 관측한 속성이 요청과 정확히 일치하면 속성 재설정·검증 호출을 생략한다. 다른 값, 읽기 전용 적용, 복구 기록, 원본 삭제 조건은 종전 검사와 오류 처리를 따른다. 6쌍 모두 확정 단계는 단축됐고 종단 시간은 3쌍에서 단축됐다. 쓰기 시간 변동을 포함한 종단 중앙값은 12 ms 늘었다.

독립 Claude 검토에서 직접 호출 측정과 패널 경로의 차이를 확인했다. 내장 해제 백엔드에만 256 KiB와 1 MiB 버퍼를 적용한 개발 실험에서는 RDP 해제 중앙값이 1,243 → 669.5 → 289 ms였다. NAS에서는 각각 350, 560, 542.5 ms였다. 패널은 파일 작업 큐에서 압축 스트림을 약 1 MiB로 묶어 임시 파일에 쓰고 검증 후 공개한다. 따라서 **백엔드 전용 버퍼 후보는 최종 제품에서 제거했다.** 위 두 표의 HC는 패널이 사용하는 열거·준비·스케줄러·네이티브 쓰기·최종 확정을 거친 시간이다. 패널 위젯을 자동 클릭하거나 화면 갱신을 기다린 시간은 포함하지 않는다.

TC는 같은 참조 ZIP을 독립 인스턴스의 실제 풀기 명령으로 해제했다. 고해상도 대기 타이머(2 ms), 출력 크기 확인 후 독점 열기, 마지막 미완료 관측 기록을 사용했다. 독점 열기 자체의 RDP 왕복은 남는다. HC와 TC 모두 완료 후 복원된 8 MiB 전체를 검증했다. 기준 ZIP의 SHA-256은 ``f5fac81abc0b7916100ea08968cb4f98c4d645232110f9484499f41091c22f8e`` 다. 순서 균형을 위해 처음 여섯 쌍은 다시 측정했다. 채택 행과 참고 행, 확정·쓰기 시간, TC 관측 구간은 `파일 작업 원시 표본 <261122_total_commander_job_samples.csv>`_ 에 수록했다.

소형 폴더와 짧은 로컬 작업 재검증
-----------------------------------------------------------------------

* 로컬 → RDP 23파일(96,486바이트) 복사에서 최초 HC 7,078.7 ms, 1차 개선 5,914.1 ms, 최종 5,592.8 ms였다. 최초 대비 21.0%, 직전 대비 5.4% 단축됐다. 최초 TC 3회 관측은 5,092.2 ms로 최종 HC가 1.10배였고, 최종 회차의 robocopy /MT:8은 1,605.1 ms로 HC가 3.48배였다. TC는 최초 관측기, HC와 robocopy는 최종 빌드 3회 중앙값이다. 서로 다른 회차의 중앙값 비교다.
* 로컬 8 MiB 복사·같은 볼륨 이동·영구 삭제는 HC 각각 13.6, 2.3, 1.9 ms였다. 고해상도 관측기로 다시 측정한 TC의 3회 중앙값은 32.5, 33.5, 27.3 ms였다. 초기 TC 수치는 아래 표에 보존했다. 로컬 결과에도 TC 명령 전달과 완료 관측 시간이 포함된다.
* 독립 검토의 세 지적을 반영했다. 최초 TC 표에 관측 편향을 명시하고 짧은 로컬 작업과 RDP ZIP을 재측정했다. 백엔드 전용 후보는 제외하고 실제 파일 작업을 검증했다. TC 측정 스크립트는 모든 소유 디렉터리 정리를 시도한 후 원래의 작업 오류를 우선 반환하며, 정리 실패 시 경로와 만료일을 기록한다.
* 최종 Qt Release는 제품 PE 서명 76개와 인벤토리 해시 366개를 확인한 뒤 D:/Utils/HyperCommander에 설치했다. iMonAGR-Win11에서 생성 12건, 7z·코퍼스 57건, 파일 전송 11건, 메타데이터 6건이 통과했다. 실제 RDP 게시·복구, ZIP 1 MiB 직전·정확한 경계·경계 초과·불완전한 마지막 블록, 취소와 CRC 오류 후 부분 출력 제거도 통과했다. 이 설치는 당시 공유 작업 트리의 변경들을 포함한다. 덮어쓴 파일과 인벤토리 백업은 ``_build/install/947860d644e847e8af703f215e6fbf07`` 에 있다. 측정 전용 로컬 실행환경·입력 복제본·임시 프로필과 테스트가 사용한 RDP·NAS 작업 폴더를 정리했다. 결과보고서, 원시 표본과 설치 백업을 보존했다.

**측정 범위와 재현**

* 단일 파일은 8 MiB의 반복 바이트다. 각 도구·경로·작업을 세 번 측정해 중앙값을 냈다. 별도 복사본을 사용했고, 복사·이동·해제 결과와 새 아카이브에서 복원한 내용을 원본 전체와 대조했다. 폴더는 합계 96,486바이트의 동일한 파일 23개다. HC 폴더 값은 직전 실측을 사용했다. RDP → 로컬은 6회이며 나머지 방향과 TC는 각 3회다. NAS에 폴더를 쓸 때 최초 8초 제한에 걸린 3회는 제외하고 대기를 60초로 늘려 3회 모두 검증했다.
* TC는 독립 프로세스에서 시작해 새 패널의 경로와 단일 선택을 확인한 뒤 내장 명령을 호출했다. 파일 작업은 기본 전송 엔진, 복사 검증 끔, 전용 설정 및 설치 패커 연결을 사용했다. 타이머는 명령 발행부터 출력의 크기·닫힘 또는 원본 제거 관측까지이며 삭제 대화상자 승인 대기는 제외했다. 폴더 완료는 항목 수로 관측한 뒤 전체 내용을 검증했다. HC는 파일 작업 스케줄러, 압축 생성 작업, 단건 해제는 승인 백엔드의 열거·해제 호출을 측정했다. 양쪽의 GUI 조작 시간 및 HC의 최종 화면 갱신 시간은 포함하지 않았다.
* 해제 입력은 각 형식에서 동일 바이트의 참조 아카이브다. 생성은 HC의 기본 전체 검증을 켜고 레벨 1을 사용했다. TC는 패커 명령에 Z1을 전달했고 결과 압축물은 ZIP 9,848바이트, 7z 1,420바이트였다. TC 플러그인의 세부 코덱 설정과 내부 검증 비용이 HC와 동일한지는 확인하지 못했다. 설치 ISO 패커 등록은 새 아카이브 생성 플래그가 없으며, 실제 ISO 생성 명령에서도 파일이 나오지 않았다. ISO 해제는 성공했다.
* 초기에 TC만 약 2 ms 간격의 일반 타이머와 원격 파일 독점 열기로 완료를 관측했다. OS 스케줄링과 네트워크 왕복이 TC 시간에 더해져 특히 짧은 작업과 근소한 차이의 순위가 바뀔 수 있다. 이 표의 TC 시간을 내부 처리시간으로 해석하지 않는다. 이후 재현 스크립트는 고해상도 대기 타이머, 예상 크기 확인 뒤의 독점 열기와 마지막 미완료 관측 시작 시각을 기록한다.
* 새 원시 자료는 `261122_total_commander_io_samples.csv <261122_total_commander_io_samples.csv>`_ 에 있다. 포함 도구는 HC, TC, 7z.exe, oscdimg와 폴더 복사의 robocopy다. ``tools/Measure-TotalCommanderIo.ps1`` 로 단일 파일 TC 측정을 반복할 수 있다. 명령 인터페이스는 `Total Commander 내부 명령 <https://www.ghisler.ch/wiki/index.php?title=List_of_internal_commands>`_ 과 `프로세스 간 호출 예제 <https://ghisler.ch/wiki/index.php/TCUtils.cpp>`_ 를 참고했다.

**격차와 수정의 연결**

* 복사·이동·삭제는 이미 본체에서 처리한다. 원격 폴더 복사에서 조상 확인·메타데이터·파일 확정 왕복 비용을 계측하고 세 호출 경로를 단축했다. 아래 전후 표에서 로컬 → RDP가 16.5%, 로컬 → NAS가 35.9% 단축됐다. RDP는 여전히 TC보다 양방향에서 느리다. NAS 폴더 복사는 TC보다 빠르지만 robocopy보다 느리다. 단일 NAS 읽기가 TC보다 느린 원인은 개별 시스템 호출까지 분리되지 않았다.
* 이동은 로컬 같은 볼륨에서 이름 변경으로 끝나지만 원격 ↔ 로컬은 복사 확정과 원본 제거를 모두 거친다. 이번 변경은 복사·확정 쪽 왕복을 줄였다. NAS → 로컬 단일 이동의 428/303 ms 중 원본 제거만의 시간은 측정하지 않았다. 영구 삭제는 원본 제거만 측정했고 로컬과 NAS에서는 TC 이하, RDP에서는 154/149 ms였다. 삭제 전용 최적화가 만든 차이로 해석할 근거는 없다.
* 최초 계획의 독립 Claude 검토를 반영해 A/A 잡음과 30쌍 판정, 코덱 옵션 대조, 원격 준비 파일의 재읽기, ISO 후방 섹터 쓰기 순서를 검증 항목으로 추가했다. ISO 후방 쓰기 순서와 원격 준비 위치는 제품에 반영했다. 코덱 빌드 옵션과 OS의 실제 디스크 쓰기량은 추가 계측 대상으로 남는다.
* 승인 호스트의 중복 검사와 형식 탐색 중 중복 열기를 줄였다. 동일 조건 전후 비교에서 RDP 입력 ZIP 해제는 1,118 → 330.5 ms였다. 위 표는 별도의 참조 ZIP을 이용한 측정이다. 로컬 ZIP 해제에는 호스트 기동·열거 비용이 남는다. 단건 백엔드 호출과 실제 패널 파일 작업의 차이는 별도로 측정했다.
* 비암호화 새 7z·ZIP은 내장 코덱을 본체에서 호출한다. 검증 시 8 MiB까지 디코딩 결과와 인코더 입력을 직접 대조해 해시 계산을 줄였다. NAS 출력에서 두 형식 모두 TC보다 빨랐고 NAS 입력 생성은 여전히 느렸다. 대형 입력은 해시 경로를 유지한다. ISO는 원격 이미지 재검증과 작은 섹터 읽기를 줄였지만 RDP 양방향 생성은 oscdimg보다 느렸다.
* 본 표에는 원격 ↔ 원격, 중첩 압축이나 원격 TEMP, 휴지통 삭제, 대용량 비압축성 데이터, 덮어쓰기, 실제 패널에서 시작하는 선택 해제의 TC 비교가 없다. 이 조합과 종전 전문 도구 기준의 판정은 별개다.

경로별 원인과 수정 내역
----------------------------------

.. list-table::
   :header-rows: 1

   * - 작업·경로
     - 느렸던 단계와 근거
     - 적용한 변경 및 남은 차이
   * - 7z·ZIP 생성 · 로컬
     - 같은 8 MiB에서 이전 호스트 첫 7z 생성 216.5 ms, 재사용 99.5 ms, 같은 비교의 직접 호출 31 ms였다. 프로세스 기동·승인 비용과 해시·해독 검증 비용이 겹쳤다.
     - 비암호화 신규 생성은 배포 코덱을 본체에서 호출하고 전용 후보에 기록한다. Windows SHA-256과 생성 형식 지정 열기로 중복 작업을 줄였다. 기본 전체 검증에는 해독 시간이 든다.
   * - ISO 생성 · 로컬
     - 64 MiB ISO에서 같은 기본 검증으로 판독기 변경 전 162 ms, 변경 후 63 ms였다. 구조 검증도 81 ms에서 47 ms로 줄었다.
     - 연속 구간은 요청한 크기대로 ReadFile에 전달하고 불필요한 seek를 생략한다. 섹터 설명자를 묶어서 읽고, 동일 크기 파일 두 개의 중복 여부는 직접 내용 비교로 판정한다.
   * - 생성 · 로컬 → RDP
     - 원격 임시 이미지에 직접 쓰고 완성 이미지를 다시 읽었다. 8 MiB ISO 전체 검증은 원격 준비·강제 flush 10,560 ms, 로컬 준비·기본 쓰기 463 ms였다. 두 설정의 개별 기여도는 미분리다.
     - 고정 로컬 임시 볼륨에서 생성·검증하고 완성한 후보를 목적지로 한 번 전송한다. 마지막 목적지 확정 및 기존 대상 확인 비용은 남는다.
   * - 생성 · RDP → 로컬
     - 같은 준비·쓰기 정책에서 판독기 변경 전후 ISO 전체 18,435 → 688 ms, 구조 9,489 → 522 ms였다. 한 차례 원본을 읽는 구조 검증에서도 큰 차이가 났다.
     - Windows ISO 판독기가 요청 크기를 보존한다. 7z·ZIP은 원본 스트림의 연속 seek와 마지막 빈 읽기를 줄였다. 입력 채널 전송 시간은 형식·데이터에 따라 다르다.
   * - 생성 · 로컬 → SMB
     - NAS 출력의 첫 7z 구조 검증 예에서 작업 build 267 ms 중 코덱 encode 14 ms였다. NAS에서 임시 후보와 검증 파일을 다루는 경로의 기여는 같은 NAS의 준비 위치 A/B로 확인했다.
     - SMB도 로컬 준비를 자동 선택한다. 예상 공간을 확보할 수 없거나 임시 폴더 생성이 실패하면 목적지 준비를 사용한다. 검증 도중 디스크가 가득 차는 경우에는 기존 오류 처리를 따른다. 최종 전송과 공개 비용을 포함한 결과를 위에 기록했다.
   * - 생성 · SMB → 로컬
     - 동일 NAS 파일을 HC가 먼저 읽으면 8 MiB ISO 구조 검증 중앙값이 390 ms, 뒤의 oscdimg는 32 ms였다. 도구 순서를 반대로 바꾸면 먼저 실행한 도구가 느려졌다. NAS 캐시·클라이언트 캐시·네트워크의 개별 기여는 미측정이다.
     - 제품은 읽을 수 있는 SMB 원본을 코덱에 직접 전달한다. 측정기는 도구별로 새 입력을 준비하고 순서를 교대한다. 위 표에는 이 보정값을 사용했다.
   * - 7z·ZIP·ISO 해제 · 로컬 및 원격 → 로컬
     - 콜드 호스트는 생성·승인·목록 열기부터 부담한다. 로컬 호스트 단독 비교에서 개선 7z 첫 호출 88.5 ms, 재사용 24 ms, CLI 28 ms였다. 원격 ZIP 단건은 추가 읽기·탐색 비용을 포함하며 왕복별 기여는 미계측이다.
     - 플러그인 파일 승인에서 이미 읽은 PE 헤더를 재사용하고 ISO는 본문을 호출자 버퍼로 읽는다. 외부 입력은 격리 호스트에서 처리한다. 다음 우선순위는 같은 입력의 열거·추출 간 열기 재사용이다.
   * - 해제 · 로컬 → SMB 또는 RDP
     - 목적지에 압축 해제한 전체 바이트를 써야 한다. 콜드 호스트 고정 비용은 있지만, 이번 단건 표본에서는 로컬 입력을 원격으로 해제할 때 HC가 7z.exe보다 짧았다. 캐시와 쓰기 완료 보장별 시간은 분해하지 않았다.
     - 동일 HC 아카이브를 양쪽에서 파일로 복원하고 전체 바이트로 확인했다. 여러 멤버를 선택하는 실제 UI 작업은 별도 인수 대상으로 남겼다.
   * - 복사 · 로컬 ↔ RDP
     - 작은 파일 23개에서 선택 개수에 따른 병렬 진입 제한과 파일별 마지막 빈 읽기가 있었다. 병렬 정책 변경 전후를 양방향 실측했다.
     - 독립 파일 준비를 최대 8개로 병렬화하고 고정 읽기 핸들은 마지막 데이터에서 EOF를 알린다. 작은 파일의 충돌 검사·순서 있는 확정은 여전히 직렬 비용을 포함한다.
   * - 복사 · 로컬 ↔ SMB
     - 중간 크기 4개와 작은 파일 23개의 결과가 크게 다르다. 작은 파일의 부모·파일 상태 확인과 목적지 확정은 파일마다 수행된다. 개별 SMB 요청 수는 계측하지 않았다.
     - 일반 원격 파일에 네이티브 복사 사용 범위를 넓히고 독립된 작은 파일 준비를 병렬화했다. NAS 출력 14 MiB는 두 robocopy 기준보다 빨랐고, 작은 파일은 양방향 모두 더 느렸다.
   * - 복사 · SMB ↔ RDP
     - 두 원격 경로를 호스트가 연결한다. 23개 파일에서 양방향 모두 robocopy /MT:8과 차이가 남았다. 왕복 횟수와 양쪽 네트워크의 개별 기여는 미측정이다.
     - 같은 병렬 준비와 EOF 변경을 사용한다. RDP의 스트리밍 경로를 유지한다. 이 조합의 정책 변경 전 기준은 수집하지 않아 개선율은 산출하지 않았다.
   * - 단일 파일 이동 · 로컬, SMB, RDP
     - 최초 탐색에서 같은 볼륨 로컬 이동은 HC/TC 2.3/42.0 ms였다. 8 MiB의 RDP → 로컬 이동은 408.5/322.3 ms였다. 볼륨 간 이동은 대상 복사 후 원본 제거가 추가된다. 각 프로그램의 원본 삭제와 리디렉터 대기 시간을 따로 분리한 값은 없다.
     - 파일별 복사와 최종 대상 확인의 공통 개선을 사용한다. 원본 제거가 허용되는 조건은 유지했다. 이번 RDP 신규 복사 수치를 이동 성능으로 환산하지 않았다.
   * - 영구 삭제 · 로컬, SMB, RDP
     - 최초 탐색의 HC/TC는 로컬 1.9/29.5 ms, NAS 10.7/45.8 ms, RDP 154.1/148.6 ms였다. 특히 5.5 ms인 RDP 차이는 외부 관측 지연과 삭제 자체를 분리해 설명할 수 없다.
     - 이번 파일 공개 변경은 삭제에 적용되지 않는다. 영구 삭제에서 원본 소멸을 같은 방식으로 감지하는 보정 측정이 남는다. 휴지통 이동은 별도 작업이다.
   * - 임시·가상·중첩 입력
     - 원본 경로를 직접 열 수 없는 입력은 코덱용 파일로 복사해야 한다. 목적지까지 원격이면 생성·재열기·게시가 같은 채널을 반복할 수 있다.
     - 직접 열 수 있는 입력은 원본 경로를 사용하고 준비 디렉터리는 필요할 때만 만든다. 로컬 임시 디스크의 쓰기 공간을 보수적으로 점검한다. 중첩 입력 자체와 원격 TEMP만 있는 환경의 종단 시간은 미측정이다.

구현과 판단
--------------------

* 7z 비암호화 신규 생성은 제품에 포함된 코덱의 경로와 해시를 고정한 상태에서 본체 작업 스레드가 전용 임시 후보를 직접 작성한다. 외부 플러그인, 기존 아카이브 편집 및 암호화에는 격리 호스트를 사용한다. SHA-256을 Windows 공급자로 계산하고 매니페스트 검사에서 이미 읽은 PE 헤더를 재사용한다.
* 파일 교체·원본 삭제 작업은 본문 검증을 강제한다. 새 ZIP·7z·ISO는 기본적으로 본문을 대조하고 생성 설정에서 이를 해제할 수 있다. ISO는 모든 모드에서 이름 공간 및 파일 위치·크기를 확인한다. 동일한 크기의 원본이 두 개일 때 중복 검사는 두 파일을 직접 비교하며, ISO 판독기는 연속된 볼륨 설명자를 묶어 읽는다.
* 원격 드라이브에 ISO를 바로 작성하면 생성과 재검증이 같은 RDP 채널을 여러 번 지난다. SMB·RDP 목적지는 고정 로컬 임시 볼륨에 여유가 있으면 로컬에서 생성·검증한 뒤 결과를 한 번 전송한다. HC_ARCHIVE_LOCAL_STAGE=0은 목적지에서 준비하고 1은 로컬 준비를 요청한다.
* 작은 원격 선택도 병렬 복사를 사용하고 16 MiB 이하의 독립 파일은 최대 8개를 준비한다. 충돌 판정과 최종 확정 순서를 유지한다. 고정한 입력의 마지막 데이터에 EOF를 표시해 파일마다 한 번씩 발생했던 추가 읽기를 줄였다.

재현 및 남은 인수 조건
--------------------------------------

* 생성 하네스는 hc_archive_creation_tests publicationBenchmark로 실행한다. HC_ARCHIVE_BENCH=1, HC_BENCH_7Z, HC_OSCDIMG를 설정하고 HC_BENCH_QUICK=1, HC_BENCH_EXTRACT=1, HC_BENCH_MIB, HC_BENCH_SOURCE_ROOT, HC_BENCH_DESTINATION_ROOT로 행을 선택한다. HC_ARCHIVE_TIMINGS=1은 작업 단계 시간을, HC_BENCH_FLUSH=1은 강제 flush 비교를 제공한다. HC_BENCH_CLI_FIRST=1은 생성 순서를 뒤집고 HC_BENCH_SEPARATE_INPUTS=1은 도구별 독립 파일을 만든다.
* 전송은 hc_file_transfer_bench_tests transfer:qt-repo 또는 transfer:medium-few로 실행한다. HC_TRANSFER_BENCH_ROOT와 OTHER_ROOT(같은 접두사)에 양 끝을 지정한다. copy-cross 연산, 축척 0.001 또는 0.01, 3회 반복이다.
* 여전히 느린 경로의 우선순위는 실제 RDP·NAS 소형 파일의 부모 확인·파일 확정 왕복, 콜드 해제의 호스트 기동·열거 중복, 대형 ISO의 읽기·쓰기 및 공개 비용이다. 파일 작업별 기존 취소·충돌·원본 삭제 보장을 유지하며 다음 비교를 진행해야 한다.
* 이 표본에는 비압축성 자료, 다수 멤버·솔리드 선택 해제, GiB급 파일, 모든 조합의 UI 종단이 포함되지 않는다. 30쌍 인수는 표기한 일부 생성 행에 한정했다. 반복 순서와 파일 캐시, 병행 빌드에 따른 변동이 있다. 한 행에서 외부 도구보다 빨랐다는 사실을 전체 동등 성능으로 확대하지 않는다.

1차 구현과 이번 측정의 범위
---------------------------------

1차 결과에서 64 MiB UDF Bridge 생성은 원본·이미지의 중복 재독을 줄여 378.5 → 154.5 ms였다. ISO 9660 단일 파일 추출은 호출자 버퍼로 직접 읽어 66.4 → 53.9 ms였고 당시 7z.exe는 39.6 ms였다. SMB 루프백의 235개 파일 복사는 준비 병렬화로 9,470.6 → 6,726.2 ms였다. 이 세 수치는 서로 다른 실험의 기준이며 이번 실제 NAS 23개 파일 또는 호스트를 포함한 ISO 추출 결과와 이어 붙여 개선율을 계산하지 않았다. 백엔드별 이전 기준과 측정 경계는 `1차 보고서 <261122_archive_performance_results.rst>`_ 에 있다.

잔여 격차를 줄이는 구현 순서
----------------------------------------

#. 작은 파일 23개 실제 RDP·SMB 복사부터 원격 요청을 세어 부모 검사, 임시 파일 생성 및 확정에 든 시간을 나눈다. 같은 작업의 부모 핸들을 재사용하고 독립 파일의 준비를 겹친 뒤, 부모 변경·취소·교체 충돌 시 기존 대상 보존을 재검사한다.
#. 단건 해제는 열거에서 확보한 호스트와 열린 아카이브를 추출까지 전달하는 경로를 비교한다. 암호·솔리드·부분 선택은 개별 벤치마크를 두고, 호스트 종료·아카이브 변경 시 이전 항목을 재사용하지 않게 한다.
#. 로컬 7z·ZIP은 코덱 인코딩과 결과 재해독을 별도로 계측한다. 전체 검증은 그대로 제공하고, 읽기 완료 후 검증이 필요한 구간과 공개 비용을 줄이는 변경부터 같은 코퍼스로 검증한다. ISO는 남은 구조 검사 및 목적지 최종 쓰기를 oscdimg와 대응시킨다.
#. 비교할 때는 임시 디스크 여유량·경로·무결성 정책을 고정하고 파일 수가 많은 코퍼스와 비압축성 GiB급 파일을 추가한다. 새 경로의 기본 채택은 같은 보장의 결과 검증과 해당 경로 30쌍 인수로 판단한다.
